# 协作规范（CONTRIBUTING）

> 本文件定义项目的提交规范、分支策略、协作流程。
> 适用于人类开发者和 AI 协作。
> 与 `CONTEXT.md`（架构约束）互补，不重复。

- 版本：v1.0
- 最后更新：2026-09-21

---

## 1. 提交规范（Commit Convention）

### 1.1 格式

采用 **Conventional Commits** 规范：

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

- **type**：英文，必填（见下表）
- **scope**：可选，模块名，英文小写
- **subject**：中文，简短描述，不超过 50 字，不加句号
- **body**：可选，详细说明，每行不超过 72 字
- **footer**：可选，关联 issue 或破坏性变更说明

### 1.2 type 清单

| type | 说明 | 示例 |
|------|------|------|
| `feat` | 新增功能 | `feat(timetable): 支持周次切换` |
| `fix` | 修复 bug | `fix(provider): 修复模块切换越界崩溃` |
| `refactor` | 重构（不改行为） | `refactor(theme): 抽取颜色解析函数` |
| `style` | 代码格式（不改逻辑） | `style: 统一缩进为 2 空格` |
| `docs` | 文档变更 | `docs(api): 补充 Course 接口清单` |
| `chore` | 构建/依赖/工具 | `chore(deps): 升级 dio 到 5.4.0` |
| `perf` | 性能优化 | `perf(grid): 减少课表重建次数` |
| `test` | 测试相关 | `test(model): 补充 Course.fromJson 测试` |

### 1.3 scope 清单

| scope | 说明 |
|-------|------|
| `model` | 数据模型 |
| `theme` | 主题系统 |
| `provider` | 状态管理 |
| `timetable` | 课表模块 |
| `exam` | 考试模块 |
| `homework` | 作业模块 |
| `message` | 消息模块 |
| `plugin` | 插件系统 |
| `skin` | 皮肤系统 |
| `settings` | 设置页 |
| `deps` | 依赖 |
| `docs` | 文档 |

### 1.4 示例

**✅ 好的提交：**

```
feat(timetable): 支持按周次过滤课程

- 添加 WeekSelector 组件
- 过滤逻辑抽取到 TimetableLogic
- 默认显示当前周

Closes #12
```

```
fix(provider): 修复导航栏越界崩溃

当用户关闭"考试"模块时，如果当前正处于考试 Tab，
index 会越界导致崩溃。改为先重置 index 再更新模块列表。
```

**❌ 差的提交：**

```
update
```

```
修复了bug
```

```
加了新功能和一些其他的东西
```

### 1.5 特殊场景

**AI 生成的代码**，在 commit message 里注明来源：

```
feat(model): 添加 Course 和 TimePlace 模型

Generated by DeepSeek R1 with prompt: docs/prompts/01-models.md
```

**破坏性变更**，在 footer 加 `BREAKING CHANGE:`：

```
refactor(model): 重命名 Course.unit 为 Course.credit

BREAKING CHANGE: Course.unit 字段已重命名，
所有引用处需同步更新。
```

## 2. 分支策略

### 2.1 主要分支

| 分支 | 用途 | 保护 |
|------|------|------|
| `main` | 稳定版本，可发布 | ✅ 受保护，禁止直接 push |
| `dev` | 开发主线 | ✅ 受保护 |

### 2.2 功能分支

命名格式：`<type>/<简短描述>`

```
feat/timetable-grid
fix/navbar-crash
docs/prompt-01
refactor/theme-engine
```

- 从 `dev` 切出
- 完成后 PR 回 `dev`
- 定期同步 `dev` 的最新代码

### 2.3 发版

- `dev` 稳定后合并到 `main`
- `main` 上打 tag：`v0.1.0`、`v0.2.0` ...
- 遵循语义化版本：`主版本.次版本.修订号`

## 3. PR 流程

### 3.1 提交 PR 前的自查

- [ ] `flutter analyze` 无错误
- [ ] 代码符合 `CONTEXT.md` 的代码规范
- [ ] 新增接口已更新到 `docs/API.md`
- [ ] 已完成的项已在 `docs/PROGRESS.md` 勾选
- [ ] commit message 符合本规范

### 3.2 PR 标题

和 commit message 格式一致：

```
feat(timetable): 完成课表网格渲染
```

### 3.3 PR 描述模板

```markdown
## 变更内容
- 实现了 xxx
- 修复了 xxx

## 相关文档
- 更新了 docs/API.md
- 勾选了 docs/PROGRESS.md 的 x.x 项

## 验收方式
1. 打开 App，切换到 xxx 页面
2. 应该看到 xxx

## 截图（可选）
（贴图）
```

## 4. 文档更新职责

| 文档 | 什么时候更新 |
|------|-------------|
| `CONTEXT.md` | 架构原则变化时（罕见） |
| `API.md` | 每次新增/修改公开接口后（必须） |
| `PROGRESS.md` | 每完成一个任务后（必须） |
| `CONTRIBUTING.md` | 协作流程变化时（罕见） |
| `prompts/*.md` | 工作流调整时 |

**核心原则**：代码和文档**同一次提交**，不要"下次再补"。

## 5. AI 协作规范

### 5.1 使用提示词

- 每次让 AI 生成代码前，从 `docs/prompts/` 中找到对应提示词
- 必须把 `CONTEXT.md` 和 `API.md` 作为前缀提供（`base.md` 里有模板）
- AI 输出后，**先自查**再保存

### 5.2 AI 生成代码的处理

- **不要**直接提交 AI 生成的代码，务必先 review
- 关键逻辑要理解，不要盲信
- 遇到不确定的，先跑一次看行为

### 5.3 记录来源

- AI 生成的关键代码，在 commit message 中注明用了哪个提示词
- 更新 `PROGRESS.md` 时，可以在备注里写"AI 生成（prompt: 01-models）"

## 6. 代码 Review 要点

自我 Review 或给同学 Review 时，重点看：

- [ ] **命名**：字段/方法名是否清晰、是否符合 Dart 规范
- [ ] **空安全**：有没有遗漏的 `?` / `!`，会不会 NPE
- [ ] **异步**：await 是否完整，异常是否处理
- [ ] **架构边界**：有没有破坏"插件不接触 UI"、"UI 不硬编码颜色"
- [ ] **性能**：列表有没有用 `ListView.builder`，Provider 有没有不必要的 notifyListeners
- [ ] **可测试性**：纯函数是否和 UI 分离
